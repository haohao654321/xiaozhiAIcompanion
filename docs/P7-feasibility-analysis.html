一、功能概述与商业对标

用户需求拆解为 4 个子功能：

  1. 上电自启：插电即工作（已实现，现有架构开机即运行）
  2. 人脸识别：识别 3 名家庭成员身份
  3. 留言投递：不在家时，家人通过 APP 发留言/语音/图片/任务，对应成员回家后机器人识别身份并播报
  4. 手机 APP：配置机器人、上传照片、留言管理
商业对标：萤石 RK3 家庭助理机器人（2024 年发布）

几乎完全一致的产品形态——RK3 核心卖点就是"本地人脸识别 → 个性化留言推送"，通过手机 APP 管理家庭成员、留言提醒。区别在于 RK3 有 7 英寸屏、3 轴云台、400 万摄像头、专用 AI 芯片，售价约 2000-3000 元。用户的项目是微型化版本：1.5 寸屏、固定摄像头、ESP32-S3 芯片，但功能逻辑可以复刻。

其他对标产品：Loona 机器狗（ChatGPT+人脸识别+APP）、耘趣家伴 AI 机器人（异地陪伴+人脸识别），均采用"本地人脸识别 + 云端消息中继 + 手机 APP"三层架构。

二、核心模块一：ESP32-S3 端侧人脸识别

2.1 技术方案：ESP-WHO 框架

乐鑫官方提供 ESP-WHO 视觉框架，内置完整的人脸检测+识别流水线，无需自己训练模型：

环节 模型 大小 ESP32-S3 实测 说明
人脸检测 MTMN (MTCNN+MobileNet) ~87KB 120-180ms/帧 240x240 输入，定位人脸边界框+关键点
特征提取 MobileFaceNet 量化版 ~196KB 80-420ms/次 128/512 维特征向量，LFW 99.2% 准确率
特征比对 余弦相似度 ~0KB (计算) <5ms 与注册库比对，默认阈值 0.52
合计 ~1.2MB ~300-700ms 3 人库比对，满足"回家识别"场景

2.2 关键优势：OV3660 已在支持列表

ESP-WHO 官方文档明确列出支持 OV2640 和 OV3660 两种摄像头。用户项目的 OV3660（硬件 JPEG、320x240 QVGA）正好在列，硬件兼容性无问题。

2.3 核心风险：ESP-WHO 与 Arduino/PlatformIO 的兼容性

这是整个方案最大的技术风险点。

ESP-WHO 基于 ESP-IDF 框架开发（使用 idf.py 编译、menuconfig 配置），而用户项目是 Arduino + PlatformIO 框架。两者不能直接混用。

有三条路径解决：

路径 做法 工作量 风险
方案 A
提取组件做 Arduino 库		 从 ESP-WHO 提取 esp-face + esp-dl + esp32-camera 组件，作为 PlatformIO 本地 lib 集成（类似已做的 esp-sr 方案） 中等
~2-3 天		 需处理 ESP-IDF API 差异、CMake→SCons 适配；但已有 esp-sr 集成经验可复用
方案 B
切 ESP-IDF 框架		 整个项目迁移到 ESP-IDF，放弃 Arduino 极大
~2-3 周		 现有所有 Arduino API 代码（WiFi、I2S、Camera、Display）需重写；不推荐
方案 C
云端人脸识别 API		 拍照→上传百度/腾讯人脸识别 API→返回身份 小
~1 天		 依赖网络、有延迟（~2s）、有 API 调用费用；但无框架兼容问题

推荐方案 A——与 esp-sr 集成模式一致，用户有经验基础。ESP32 Arduino Core 3.x 已内置部分 esp-face 组件，提取集成的难度可控。

2.4 人脸注册流程

ESP-WHO 支持"离线注册"：用户在 APP 上拍 3 张正脸照 → 上传云端 → 云端提取特征向量（或 ESP32 本地提取） → 存储到 Flash/SD 卡。之后每次检测到人脸时，提取特征与注册库比对即可识别身份。

3 人的特征库仅占 3 x 128 维 x 4 字节 = 1.5KB，可存 NVS 或 SPIFFS。

三、核心模块二：云端消息中继架构

3.1 为什么需要云端

用户在外出时通过 APP 发留言，机器人不在同一局域网。需要一个"中继站"让 APP 和机器人通信。标准 IoT 方案是 MQTT + HTTP 文件服务。

3.2 通信架构设计

数据类型 上行 (APP→机器人) 下行 (机器人→APP) 协议
文字留言 APP → MQTT Broker → 机器人 MQTT publish 即时推送 MQTT (JSON, <4KB)
语音留言 APP 录音 → HTTP 上传 → URL → MQTT 通知 机器人收到 URL → HTTP 下载 → 播放 HTTP POST + MQTT
图片 APP 选图 → HTTP 上传 → URL → MQTT 通知 机器人 HTTP 下载 → SD 卡缓存 → LCD 显示 HTTP POST + MQTT
任务/提醒 APP 设置定时 → 云端存储 → 到点 MQTT 推送 机器人收到 → TTS 播报 MQTT + 定时器
人脸注册 APP 拍照 → HTTP 上传 → 云端/本地提取特征 特征向量推送到机器人 NVS HTTP + MQTT

图片传输的坑：ESP32 的 MQTT 库 (PubSubClient) 单条消息限制约 64KB，一张 JPEG 图片通常 20-100KB。标准做法是 HTTP 上传图片到服务器 → 获取 URL → MQTT 只发 URL 字符串。机器人收到 URL 后用 HTTPClient 下载到 SD 卡。这条路径成熟可靠。

3.3 云端服务选项

方案 成本 延迟 适合度 说明
免费公共 MQTT Broker
(EMQX 免费版 / HiveMQ)		 0 元 ~100-500ms 可用 有连接数/消息量限制，不稳定时丢消息；适合验证阶段
阿里云 IoT 平台
(MQTT + OSS 存储服务)		 ~5-10 元/月 ~50-100ms 推荐 稳定可靠、国内低延迟、有 SDK、能和天猫精灵生态联动
自建 VPS
(Mosquitto + Nginx + SQLite)		 ~30-50 元/月 ~50-200ms 可选 完全自控、灵活；需自己运维
树莓派本地服务器 一次性 ~¥300 ~10ms (局域网) 有条件 需额外硬件，且 APP 在外网时无法访问

推荐阿里云 IoT——用户家中已有天猫精灵生态（阿里云生活物联网平台），可以直接复用账号体系。MQTT 消息 + OSS 存储图片，月成本约 5-10 元，延迟可控。记忆中已记录的 P8 智能家居方向也走阿里云 MQTT，可统筹。

3.4 ESP32 端资源消耗

  • PubSubClient 库：~50KB Flash + ~15KB RAM
  • HTTPClient：已有（STT/LLM/TTS 在用）
  • SD 卡缓存：留言图片/语音下载后存 SD 卡，已有 SD 接口
  • MQTT 与现有 HTTPS 对话共存：ESP32-S3 WiFi 足够支撑双连接，但需注意 TLS 内存开销（~50KB Flash / ~15KB RAM），记忆中已评估"无压力"

四、核心模块三：手机 APP

4.1 技术选型

框架 语言 跨平台 BLE 配网 IoT 生态 推荐度
Flutter Dart Android + iOS flutter_blue_plus esp_smartconfig 包 首选
React Native JS/TS Android + iOS react-native-ble-plx 社区包 可选
微信小程序 JS 仅微信内 不支持 BLE 需 WiFi 配网替代 受限

推荐 Flutter——一套代码同时出 Android + iOS，社区有成熟的 ESP32 BLE 配网方案（esp_smartconfig 包）和 MQTT 客户端包，与 IoT 设备交互的案例最多。Dart 语言对有 JS/Python 基础的人上手快。

4.2 APP 功能模块

页面 功能 对应云端
设备配网 BLE 扫描 → 绑定设备 → WiFi 配网（SmartConfig 或 BLE 传 SSID/密码） 设备绑定记录
家庭成员管理 添加成员 → 拍 3 张正脸照 → 上传注册 人脸特征库
留言中心 选收件人 → 文字/语音/图片 → 发送 MQTT + HTTP 文件服务
任务提醒 设定时任务（如"提醒妈妈吃药 8:00"） 定时器 + MQTT
消息状态 查看留言是否已被机器人播报（已读/未读） 机器人回传状态
设置 音量/阈值/人格 prompt 等 NVS 参数下发

4.3 开发工作量

Flutter APP 开发需要一定的前端开发能力。对于有编程基础的人：

  • 配网 + 基本框架：~2-3 天
  • 留言/图片/语音发送：~2-3 天
  • 人脸注册上传：~1 天
  • 任务提醒 + 设置页：~1-2 天
  • 调试优化：~2-3 天
  • 合计约 1-2 周（有一定 Flutter 基础的话）

5.2 Flash 分区规划

当前分区表：

分区 偏移 大小 当前用途 扩展后用途
factory (app) 0x10000 5MB 固件 ~1.9MB (38.7%) 固件 + 人脸模型 ~3.1MB (62%)，够用
model (srmodels) 0x520000 3MB wakenet+multinet ~2.5MB 不变（人脸模型编入固件不放这）
spiffs 0x820000 ~8MB 未使用 人脸特征库 + 留言缓存 + 配置

Flash 资源充足：人脸识别模型 ~1.2MB 编入固件后，factory 分区 5MB 还剩 ~1.9MB 空间。SPIFFS 有 8MB 可用于存储特征库、留言缓存。PSRAM 8MB 完全够用推理缓冲。

物品 用途 成本 必要性

七、实施路线图建议

建议分 3 期实施，每期可独立验证：

第一期：人脸识别 MVP（~1 周）

  • 目标：机器人能识别 3 人身份并喊名字
  • 工作：
    1. 提取 ESP-WHO 组件集成到 PlatformIO（方案 A）
    2. 串口/Web 注册 3 张人脸（调试阶段先不走 APP）
    3. 上电后或 BOOT 键触发 → 拍照 → 识别 → TTS "欢迎回来，主人"
    4. Flash 分区调整 + 编译验证
  • 验证标准：3 人随机站摄像头前，识别准确率 >90%，延迟 <2s

第二期：云端消息中继（~1-2 周）

  • 目标：APP 能发留言，机器人能收能播
  • 工作：
    1. 阿里云 IoT 平台开通 + MQTT Broker 配置
    2. ESP32 端集成 PubSubClient，订阅消息 topic
    3. HTTP 文件服务（阿里云 OSS 或简单 VPS）存图片/语音
    4. 机器人收到消息 → SD 卡缓存 → 识别到对应主人时 TTS 播报 + LCD 显示
  • 验证标准：手机发一条文字留言，对应主人回家后机器人自动播报

第三期：手机 APP 完整版（~1-2 周）

  • 目标：完整 APP，家人能用
  • 工作：
    1. Flutter APP 框架 + BLE 配网
    2. 人脸注册页（拍照上传）
    3. 留言中心（文字/语音/图片）
    4. 任务提醒 + 设置页
  • 验证标准：家人从 APP 发送留言到机器人播报，全流程 <10s

八、结论

可行性评估：可以做，但有 1 个关键风险点需先验证
维度 结论 信心
人脸识别 ESP-WHO 官方框架支持 OV3660 + ESP32-S3，模型小、精度够、本地运行
但 Arduino/PlatformIO 集成是关键风险点，需先验证方案 A 可行性		 80%（方案 A 失败可退方案 C）
云端消息 MQTT + HTTP 标准方案，ESP32-S3 资源够用，阿里云低成本 95%
手机 APP Flutter 方案成熟，社区案例多，1-2 周可出可用版本 90%
硬件 现有硬件基本够用，仅需补一张 SD 卡（~¥20） 100%
总成本 SD 卡 ¥20 + 云服务 ¥5-10/月 + APP 开发时间 1-2 周 -

建议的第一步行动

在正式决策前，建议先花半天做一个 "ESP-WHO 组件提取验证"——在现有 PlatformIO 项目里尝试集成 esp-face 库，编译一个最小人脸检测 demo。如果编译通过并能跑检测，方案 A 就确认可行，后续按路线图推进。如果编译失败且排查后确认无法集成，则退方案 C（云端识别），虽然牺牲延迟和离线能力，但功能仍然完整。

这个验证不需要改现有代码，只需新建一个测试分支即可，风险可控。
